# Centralized route registry and app-level error boundary

This change consolidates route definitions scattered across Navbar, Footer, and sitemap into a single typed registry (`app/lib/routes.ts`), then adds two new app-level files: an error boundary (`app/error.tsx`) for runtime crash recovery and a web manifest (`app/manifest.ts`) for PWA metadata. The approach uses filter-and-map helpers over a flat route array with boolean flags (`includeInNav`, `includeInSitemap`) and an optional category for footer grouping. The error boundary mirrors the existing not-found page styling.

Watch for: The `Home` route has no `category` and is silently excluded from the footer (confirmed) — likely intentional but undocumented. The manifest references only `/favicon.ico` with `sizes: "any"`, which may produce blurry icons on high-DPI mobile home screens (likely). `getNavRoutes()` is called at module top-level in a `"use client"` component, meaning it runs on every page load rather than being computed once at build time (confirmed, minor).

**Verdict**: APPROVED

## High-level view

The route registry replaces three inline arrays with one source of truth. "Home" having no `category` creates a silent contract: any route without a category is invisible in the footer. A discriminated `includeInFooter` flag would make this explicit.

The error boundary renders a retry button and exposes `error.message` in development only (no sensitive details leak in production). The page text says "return to the home page" but offers no link to do so — only a retry button.

The manifest is minimal — one favicon entry, dark theme colors matching the app's existing palette. For PWA install prompts on mobile, Android and iOS expect purpose-specific icons at multiple resolutions; a single ICO file won't satisfy that.

## Route registry design and the category gap

The registry uses a flat array with boolean inclusion flags and an optional `RouteCategory`. The helpers project this array into the shape each consumer needs — nav gets `{ href, label }[]`, footer gets `Record<RouteCategory, ...>`, sitemap gets `string[]`.

The subtle contract: `getFooterRoutes()` iterates the array and pushes into pre-initialized category buckets. Any route where `category` is `undefined` (currently only `"/"`) is silently skipped. There's no runtime error and no compile-time warning. If someone adds a new route and forgets `category`, it vanishes from the footer without explanation.

```typescript
for (const route of ROUTES) {
  if (route.category) {                // ← undefined means "not in footer"
    grouped[route.category].push(...)
  }
}
```

A discriminated `includeInFooter: boolean` flag (like the existing `includeInNav`) would make this explicit rather than relying on the absence of a field.

## Error boundary: copy vs. controls mismatch

The error page tells the user they can "try again or return to the home page" but the only interactive element is the retry button. The not-found page provides a "Back to Home" link in the same visual position. Adding a secondary link or removing the "return to the home page" clause would fix the discrepancy.

## Manifest icon coverage

The manifest declares a single icon:

```typescript
icons: [{ src: "/favicon.ico", sizes: "any", type: "image/x-icon" }]
```

Chrome's PWA installability check requires a 192x192 PNG icon. Safari on iOS uses the `apple-touch-icon` link tag, not the manifest, but Android relies on the manifest `icons` array. If the intent is only to produce a valid `manifest.webmanifest` route (not to pass Lighthouse PWA audit), this is acceptable as-is. If PWA install is a goal, 192x192 and 512x512 PNG entries are needed.
